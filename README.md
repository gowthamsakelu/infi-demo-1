# Ruyi Admin

Ruyi Admin is a travel operations admin panel for managing bookings and inquiries.

![PHP](https://img.shields.io/badge/PHP-%5E8.2-777BB4)
![Laravel](https://img.shields.io/badge/Laravel-12-FF2D20)
![Database](https://img.shields.io/badge/Database-SQLite-003B57)

## Features

- **Bookings** – list, search, category filter, status tabs, bulk select, Assign, and Mark as Paid / Unpaid (saved to the database).
- **Inquiries** – lead list with status tabs (New, Ongoing, Warm, Hot), search, category filter, and bulk Assign.
- **Follow-ups and notes** – schedule a follow-up (Follow-up, Called with outcome, CC) from the ⋮ menu, and add quick notes inline. Both appear in the customer's Lead Flow / Journey.
- **Details view** – Outlook-style split view on desktop (the detail opens full width where the split does not fit), and a bottom sheet on phones. Same content for Bookings and Inquiries.
- **Assign flow** – one shared sheet for team members, vendors and contacts, from the ⋮ menu or the bulk bar.
- **Responsive** – two layouts, mobile and desktop, that switch live when the window is resized, the device is rotated or a foldable is folded or unfolded. Tablets use the desktop layout.
- **REST API** – JSON endpoints for bookings, inquiries and follow-ups.

Dashboard, Calendar, More and Settings appear in the navigation as placeholders and are not built yet.

## Tech stack

| Area | Technology |
| --- | --- |
| Backend | Laravel 12, PHP 8.2+ |
| Database | SQLite (default) |
| UI | Plain JavaScript (ES modules) and one CSS file, served from `backend/public` |
| Extra | A Livewire bookings page at `/livewire` |
| Tests | PHPUnit 11 |

The UI needs no build step: assets are served as-is and versioned by file time.

## Requirements

- PHP 8.2 or newer with the `pdo_sqlite`, `mbstring`, `openssl`, `fileinfo` and `tokenizer` extensions
- Composer 2
- Docker (optional, for the container setup)

## Getting started

```bash
git clone <repository-url>
cd Admin_Project_LARAVEL/backend
composer install
cp .env.example .env
php artisan key:generate
php artisan migrate --seed
php artisan serve --port=8000
```

Open <http://127.0.0.1:8000>. The seeder loads staff, vendors, contacts, 12 bookings and 8 sample inquiries.

### With Docker

```bash
docker compose up --build
```

The app is then available at <http://localhost:8000>. See `DEPLOYMENT_RENDER.md` for deploying to Render.

## Environment variables

Copy `backend/.env.example` to `backend/.env`. These are the ones that matter:

| Variable | Default | Purpose |
| --- | --- | --- |
| `APP_KEY` | empty | Generated by `php artisan key:generate` |
| `APP_ENV` / `APP_DEBUG` | `local` / `true` | Set `APP_DEBUG=false` in production |
| `DB_CONNECTION` | `sqlite` | Database driver |
| `DB_DATABASE` | `database/database.sqlite` | SQLite file path |
| `CACHE_STORE` | `database` | Use `file` if the cache table does not exist |

## Pages and routes

The UI is a single page that switches by URL hash.

| Page | URL | Description |
| --- | --- | --- |
| Bookings | `/#bookings` | Bookings list, details, assign, payment status |
| Inquiries | `/#inquiries` | Leads, follow-ups, quick notes, assign |
| Livewire bookings | `/livewire` | Older Livewire version of the bookings page |
| Health check | `/up` | Returns 200 when the app is running |

`/enquiries` redirects to `/inquiries`, which opens `/#inquiries`.

### API

| Method | Endpoint | Description |
| --- | --- | --- |
| GET | `/api/bookings` | List bookings (`category`, `tab`, `search`) |
| GET | `/api/bookings/{id}` | One booking |
| PATCH | `/api/bookings/{id}/payment` | Set status to `Paid`, `Pending` or `Part Paid` |
| POST | `/api/bookings/assign` | Assign bookings to a team member, vendor or contact |
| POST | `/api/bookings/{id}/guests` | Add a guest |
| PUT | `/api/bookings/{id}/special-requirements` | Update special requirements |
| GET | `/api/inquiries` | List inquiries (`status`, `category`, `search`, `from`, `to`) |
| POST | `/api/inquiries/assign` | Assign inquiries |
| POST | `/api/inquiries/{id}/follow-ups` | Save a follow-up (`type`, `date`, `time`, `comment`) |
| POST | `/api/inquiries/{id}/notes` | Save a quick note (`comment`, max 500 characters) |
| GET | `/api/follow-ups?phone=` | Follow-ups and notes for a customer, newest first |
| GET | `/api/metadata` | Staff, vendors and contacts |

The app has no login yet. Actions are recorded for staff member `ST-05` unless `created_by` is sent. Because there are no users or roles, there are **no permission or policy checks**: the itinerary API validates data (types, lengths, at most 60 days and 100 events per day) but does not decide who may edit. Add authorization when login is introduced.

## UI conventions

- **One component per job.** Bookings and Inquiries share the row, action cell (Phone, WhatsApp, ⋮), ⋮ menu, category dropdown, status tabs, bulk bar, bottom sheets, Assign sheet and detail pane. They live in `backend/public/js/shared/`.
- **Icons** come from `shared/icons.js` only.
- **Tokens** such as row sizes, safe-area insets and motion timings (`--motion-fast`, `--motion-base`, `--motion-slow`, `--ease-out`) are CSS variables in `style.css`. Every overlay animates only `transform` and `opacity` with these tokens, and respects reduced-motion.
- **No automatic keyboard.** Sheets and menus never focus an input when they open; focus goes to the dialog itself.
- **Two layouts only.** `js/shared/layout.js` is the single switch: mobile below 700px, or on a touch phone turned sideways (short screen side under 500px); desktop everywhere else, tablets included. It sets `<html data-layout="mobile|desktop">`, which the CSS keys off, and fires `layout-changed` so open overlays close cleanly on rotate, fold or resize.
- **Fitting the desktop layout.** Below 1100px the sidebar is an icon rail that expands over the content when the logo is tapped; below 1000px an open detail takes the whole content area (the X returns to the table); below about 1000px the table scrolls sideways inside its own card.
- **Touch:** controls are at least 40px on touch screens, and nothing depends on hover.

## Loading and performance

- Fonts (Plus Jakarta Sans, Inter) are self-hosted in `backend/public/fonts` and preloaded. The app waits up to 1.5 seconds for them before the first render, so text does not shift when they arrive.
- `index.html` contains a small boot skeleton and preloads the JavaScript modules, so the first paint is stable.
- Lists keep their previous rows while search, tabs or filters change. Row actions (assign, mark paid) update only the affected row and roll back if the server rejects them.
- The `/` route versions the entry CSS and JS by file time, and `public/.htaccess` turns on compression, revalidation for scripts and styles, and long caching for fonts and images.
- On deploy run `php artisan migrate --force`. The start script already caches config, routes and views.

## Keyboard checklist for a real phone

An emulator cannot reproduce a real on-screen keyboard, so run these on a phone against the deployed site, at the narrowest width you have. Expected result everywhere: the keyboard never opens by itself, the focused field stays visible above the keyboard, the footer buttons stay visible, no page shows below a sheet, and the bottom nav hides while typing and returns without a jump.

### Android (Brave and Chrome)

Do the whole list once in Brave and once in Chrome. Also try with the address bar collapsed and expanded.

1. Bookings: tap a row's ⋮, then Assign. The keyboard must not open. Tap Search: the sheet shrinks above the keyboard.
2. Tap Optional Note, then "Add new member" (name, phone): each field is visible above the keyboard.
3. Inquiries: ⋮ then Follow-up, tap the comment field. Tap the date and time fields: the system picker opens and the sheet is not covered.
4. Open a booking, Itinerary tab, Add Event: Title and Time fields; choose "Add new day" and type its title.
5. Add Day: the title field. Edit customer: scroll the form with the keyboard open.
6. Inquiries: scroll to the last row, tap its quick note. The row stays visible.
7. Close the keyboard with the back gesture: everything returns with no jump.

### iPhone (Safari)

Do the list in Safari, then once more added to the Home Screen if you use it that way.

1. Same steps 1 to 6 as Android. Nothing may zoom when a field is tapped (fields are 16px or larger).
2. Tap a field, then drag the sheet or scroll its list: the page behind must not scroll.
3. Rotate to landscape with the keyboard open: the sheet still fits above the keyboard.
4. Tap the date field in Follow-up: the iOS date wheel opens and the Save button is still reachable.
5. Dismiss the keyboard by tapping outside the field: the bottom nav returns without a jump.

### Browser tests that run without a phone

`backend/tests/e2e/` has two Playwright scripts. Playwright is not a project dependency; install it outside the app (`npm i playwright && npx playwright install chromium`) and run them against a running app:

```bash
BASE=http://127.0.0.1:8000/ node backend/tests/e2e/input-audit.mjs
BASE=http://127.0.0.1:8000/ node backend/tests/e2e/viewport-matrix.mjs
```

`viewport-matrix.mjs` adds days and events to BK-5022, so re-seed afterwards (`php artisan db:seed --force`).

## Troubleshooting

- **`vendor/autoload.php` not found** – run `composer install` in `backend/`.
- **"No application encryption key"** – run `php artisan key:generate`.
- **"no such table: cache"** – run `php artisan migrate`, or set `CACHE_STORE=file` in `.env`.
- **Inquiries stay empty or show an error** – the page needs the Laravel server for its API. Open it through `php artisan serve`, not as a static file.
- **Old screens after an update** – the entry CSS and JS URLs carry a version based on file times, and `public/.htaccess` makes browsers revalidate scripts and styles, so a redeploy is picked up on the next load. If a phone still shows an old screen, reload once.
- **Reset the sample data** – run `php artisan migrate:fresh --seed`.
